  • The statement is the specification: a precise claim about every input.

  • The proof is an argument that Lean checks, step by step.

  • If Lean accepts it, the claim holds for all a and b.

The essential ingredients of formal verification.

Key point: the checker is mechanical and small. You do not have to trust the proof's author, human or AI. You do have to trust the spec.

What do you actually get?

Guaranteed

  • The spec holds for all inputs

  • No panics, overflows, or out-of-bounds accesses, if the spec says so

  • Every case considered, including the ones you forgot

Still trusted

  • The spec: does it say what you mean?

  • The model: does the Lean code faithfully reflect the Rust (or EVM, or…) code?

  • The toolchain: compiler, hardware, Lean's kernel

Formal verification doesn't remove trust. It reduces the trust surface into a few small places you can review.

The trusted computing base

The trusted computing base (TCB) is everything a guarantee depends on that the proof does not check. For this workshop:

  • Lean's kernel: the small program that checks every proof

  • Axioms: Lean's standard ones, plus anything left as sorry (#print axioms lists them)

  • The specification: the theorem statements, which you have to read

  • The model: a transltion from source language into Lean

  • The compiler and hardware: what actually runs the Rust code

The goal is a TCB that is accounted for, small, and reviewable.

Introduce the term: people will hear it in every FV conversation. Each item comes back later: the model in Part 4 ("Translating Rust to Lean"), axioms and sorry in "Check what a proof rests on", the spec in "What a proof does not tell you".

Why now?

  • Ethereum's roadmap needs high assurance: clients, zkEVMs, cryptography.

  • Tools like Lean have matured: real Rust code can be translated and verified.

  • AI can write proofs. The kernel checks them, so a wrong proof is simply rejected.

The bottleneck moves from writing proofs to reading and reasoning about specs.

That's a skill you can start learning today.

Proof by induction

Every list is built in one of two ways: it is empty, [], or it is b :: bs, an element b in front of a shorter list bs. So [10, 20, 12] is 10 :: 20 :: 12 :: [].

To prove that a property P holds for every list, prove two things:

  1. Base case: P [] holds.

  2. Inductive step: if P bs holds (the induction hypothesis), then P (b :: bs) holds.

P(\texttt{[]}) \;\Rightarrow\; P(\texttt{[12]}) \;\Rightarrow\; P(\texttt{[20, 12]}) \;\Rightarrow\; P(\texttt{[10, 20, 12]}) \;\Rightarrow\; \cdots

Like dominoes: the base case knocks over the first, and the step makes each one knock over the next. (On numbers it's the same idea: prove P 0, and that P n implies P (n + 1).)

The next slide is exactly this in Lean: the nil case is the base case, and in the cons case ih is the induction hypothesis.

Induction: for all lists

Part 4: Verifying real Rust

The same transfer, now as Rust code, where numbers are 64 bits and arithmetic can panic.

~20 minutes for Part 4.

From Rust to Lean, automatically

To prove anything about Rust code, it first has to become Lean. Tools do this from the Rust compiler's own view of the program:

Tool

How it works

Aeneas (with Charon)

Rust → a pure functional model in Lean; specs and proofs are written in Lean

hax

Rust → Lean (and other provers); specs can be written as attributes on the Rust code

Today we write the translation by hand, so you can see every step. It looks like what these tools produce: u64s with bounds, a Result for panics, one step per Rust operation.

Talk about translation tools in general here. The point to land: a tool replaces trusting a person's translation with trusting the tool; either way the translation is in the TCB. Nothing in the rest of this section depends on how the Lean was produced.

The same transfer, in Rust

pub fn transfer(
    from_bal: u64,
    to_bal: u64,
    amount: u64,
) -> Option<(u64, u64)> {
    if amount <= from_bal {
        match to_bal.checked_add(amount) {
            Some(new_to) => {
                let new_from = from_bal - amount;
                Some((new_from, new_to))
            }
            None => None,
        }
    } else {
        None
    }
}

New compared to the model: u64 is 64 bits. Additions can overflow, and in Rust, overflow is a panic.

rust/src/lib.rs

Point out checked_add: the developer thought about overflow here.

What a u64 operation means

/-- Rust's `a - b` on `u64`: panics if the result would be negative. -/ def sub (a b : U64) : Result U64 := if b.val ≤ a.val then ok ⟨a.val - b.val, bya:U64b:U64⊢ a.val - b.val < 2 ^ 64 have := a.isLta:U64b:U64this:a.val < 2 ^ 64⊢ a.val - b.val < 2 ^ 64; omegaAll goals completed! 🐙⟩ else panic

  • U64: a natural number val with a proof that val < 2^64.

  • Result: either ok v, or panic if the Rust code would panic.

The prelude gives one such definition for each Rust operation we use: +, -, /, %, checked_add, casts.

/-- `transfer` in `rust/src/lib.rs`. -/ def transfer (fromBal toBal amount : U64) : Result (Option (U64 × U64)) := do if amount ≤ fromBal then match U64.checkedAdd toBal amount with | some newTo => let newFrom ← U64.sub fromBal amount return some (newFrom, newTo) | none => return none else return none

Line by line: each Rust operation that can panic becomes a call returning a Result, and each let x = e; becomes let x ← e, which stops at the first panic.

What a proof does not tell you

def brokenTransfer (_fromBal _toBal _amount : Nat) : Option (Nat × Nat) := none
theorem brokenTransfer_conserves {fromBal toBal amount newFrom newTo : Nat} (h : brokenTransfer fromBal toBal amount = some (newFrom, newTo)) : newFrom + newTo = fromBal + toBal := byfromBal:NattoBal:Natamount:NatnewFrom:NatnewTo:Nath:brokenTransfer fromBal toBal amount = some (newFrom, newTo)⊢ newFrom + newTo = fromBal + toBal simp [brokenTransfer] at hAll goals completed! 🐙

True, proved, and useless: this "transfer" never succeeds. A spec that only talks about success is satisfied by code that always fails.

Trust, carefully

When someone says "it's formally verified", ask:

  1. What is the spec? Read the theorem statements. Are they strong enough?

  2. What is the model? What translated the code, and what does it leave out?

  3. What is assumed? #print axioms, sorry, and unverified dependencies.

This is exactly the review you need when an AI writes the proofs for you: let the machine prove it; you read the statement.

Takeaways

What to remember from today.

Four things to remember

  1. Tests check some inputs; a proof covers all of them.

  2. You trust the checker, not the prover. Lean's small kernel checks every proof, whoever wrote it: a person, a tactic, or an AI.

  3. Real code has edges a model doesn't, like overflow and panics. When a proof gets stuck, the leftover goal often points straight at a bug.

  4. Trust moves; it doesn't vanish. Read the spec, know the model, check #print axioms. That's your TCB.
